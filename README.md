# travel-planner

Бэкенд планировщика самостоятельных путешествий. Python 3.13, uv, FastAPI, PostgreSQL 18, асинхронный SQLAlchemy Core и Alembic. Код организован по слоям шаблона [Common](https://github.com/mikryukoff/Common.git).

## Локальный запуск

Установите uv и запустите Docker с Compose. Выполняйте команды из корня репозитория. Compose поднимает PostgreSQL, а uv запускает бэкенд на вашей машине.

```bash
uv sync --python 3.13 --group dev
cp .env.example .env  # PowerShell: Copy-Item .env.example .env
docker compose up -d --wait db
uv run alembic -c backend/alembic.ini upgrade head
uv run travel-import
uv run uvicorn backend.app.main:app --loop asyncio:SelectorEventLoop --reload
```

Документация API доступна по адресу <http://127.0.0.1:8000/docs>.

Параметр `--loop asyncio:SelectorEventLoop` позволяет запускать асинхронный Psycopg на Windows. Сохраняйте его и при запуске без `--reload`. [Документация Psycopg](https://www.psycopg.org/psycopg3/docs/advanced/async.html)

- `GET /health/live` проверяет работу приложения.
- `GET /health/ready` проверяет соединение с БД и наличие таблицы мест. При сбое возвращает 503.

Для существующего PostgreSQL задайте `DATABASE_URL` в `.env` и выполните миграцию и импорт. Переменная окружения имеет приоритет над `.env`.

Если порт `5432` занят, задайте в `.env` значение `POSTGRES_PORT=5433` и тот же порт в `DATABASE_URL`. Затем запустите `docker compose up -d --wait db`. Внутри контейнера PostgreSQL использует порт `5432`.

## Как устроен код

| Путь | Что здесь искать |
| --- | --- |
| [`backend/app/main.py`](backend/app/main.py) | Фабрика FastAPI, подключение роутеров и обработчиков ошибок, закрытие пула БД при остановке |
| [`backend/app/api/`](backend/app/api/) | Роуты в `routers/`, форматы запросов и ответов в `schemas/`, сборка сервисов и проверка токена в `dependencies.py` |
| [`backend/app/application/`](backend/app/application/) | Сценарии каталога, поездок, гостевых сессий и импорта. Здесь проверяются права на поездку, её версия и совместимость остановок |
| [`backend/app/domain/`](backend/app/domain/) | Правила длительности поездки и модель фильтров каталога. Обычный Python без HTTP и БД |
| [`backend/app/infrastructure/`](backend/app/infrastructure/) | SQL-запросы в `repositories/`, таблицы SQLAlchemy Core в `db/models/`, пул и транзакции в `db/database.py`, чтение файлов базы знаний в `knowledge.py` |
| [`backend/app/security/`](backend/app/security/) | Генерация и хеширование гостевых токенов |
| [`backend/app/config/`](backend/app/config/) и [`backend/app/shared/`](backend/app/shared/) | Загрузка настроек, общий класс прикладных ошибок и доступ к логгеру |
| [`backend/alembic/`](backend/alembic/) и [`backend/alembic.ini`](backend/alembic.ini) | История миграций и конфигурация Alembic |
| [`backend/scripts/`](backend/scripts/) и [`data/knowledge/`](data/knowledge/) | Команда импорта, исходные данные и их валидатор |
| [`backend/tests/`](backend/tests/) | Быстрые проверки правил и интеграционные тесты API и импорта на PostgreSQL |

Например, `PUT /api/v1/trips/{trip_id}/itinerary` проверяет тело запроса по схеме в `api/schemas/trips.py`. Роутер передаёт ID гостя и программу в `application/trips.py`. Сервис проверяет владельца, версию и дни поездки, затем вызывает `infrastructure/repositories/trips.py` для замены остановок. Зависимость FastAPI передаёт проверке токена и сервису одно соединение и фиксирует транзакцию до успешного ответа.

Для нового эндпоинта добавьте схему и роутер в `api/`, сценарий в `application/`, а SQL-запросы в репозиторий. Подключите зависимости в `api/dependencies.py`. Чистые правила, которые можно проверить без БД, размещайте в `domain/`. Импортируйте модули от корня через `backend.app.*`. Прикладные ошибки преобразуются в JSON с полем `detail`, а ошибки валидации запроса сохраняют стандартный формат FastAPI.

## База знаний

Исходные материалы находятся в `data/knowledge`. Импорт запускает существующий валидатор, затем одной транзакцией обновляет 16 городов, категории, 742 места и 48 черновиков маршрутов. Повторный запуск обновляет записи по стабильным ID и заменяет связи импортируемых записей. Записи, отсутствующие в новой выгрузке, сохраняются. Одновременные импорты сериализуются транзакционной блокировкой PostgreSQL.

Основные поля и связи вынесены в столбцы и таблицы. Полные исходные карточки хранятся в `payload` JSONB, включая источники, расписания, ограничения достоверности и атрибуцию OSM. Картографические кандидаты остаются в исследовательских файлах. Их отбор в каталог выполняется отдельно.

```bash
uv run python data/knowledge/validate_knowledge.py
uv run travel-import --directory data/knowledge
uv run alembic -c backend/alembic.ini current
```

Изменения схемы оформляются новой миграцией.

```bash
uv run alembic -c backend/alembic.ini revision --autogenerate -m "describe schema change"
uv run alembic -c backend/alembic.ini upgrade head
```

Перед применением проверьте сгенерированную миграцию. Учётные данные в `.env.example` предназначены для локальной разработки. Для остановки базы используйте `docker compose stop db`, данные сохраняются в именованном томе.

## API каталога

Все эндпоинты доступны в Swagger по `/docs`.

- `GET /api/v1/cities` возвращает города с фактическим количеством мест в БД.
- `GET /api/v1/categories` возвращает справочник категорий.
- `GET /api/v1/places` возвращает краткие карточки мест.
- `GET /api/v1/places/{place_id}` возвращает полную исходную карточку со статусами достоверности и источниками. Для неизвестного ID возвращается 404.
- `GET /api/v1/places/map` возвращает маркеры мест с координатами без статуса `conflicting`.

Список мест и карта принимают одинаковые фильтры.

| Параметр | Значение |
| --- | --- |
| `city_id` | ID города, например `kazan` |
| `category_id` | Одна категория, например `food` |
| `q` | Поиск подстроки в названии, описании и адресе без учёта регистра, включая кириллицу |
| `entity_type` | Тип места, например `restaurant` |
| `route_ready` | Готовность места к использованию в проверенном маршруте |
| `has_coordinates` | Наличие координат без отмеченного конфликта |
| `min_lat`, `max_lat`, `min_lon`, `max_lon` | Прямоугольная область карты, все четыре параметра вместе |
| `limit`, `offset` | Размер страницы от 1 до 200 и смещение от 0. По умолчанию 50 и 0 |

Фильтры применяются совместно. Неизвестный ID города или категории даёт пустую выборку. Пустой поисковый запрос и некорректные границы дают 422. Прямоугольник задаётся с минимумом не больше максимума и подходит для городских областей. `%` и `_` в поиске трактуются как обычные символы.

Ответ списка и карты содержит `items`, `total`, `limit`, `offset` и `attribution`. `total` учитывает все фильтры до пагинации. Сортировка выполняется по названию и ID. Для загрузки следующих маркеров увеличивайте `offset` до достижения `total`. На карте `has_coordinates=false` даёт пустую выборку. В сочетании с границами этот параметр вызывает 422.

```bash
curl 'http://127.0.0.1:8000/api/v1/cities'
curl 'http://127.0.0.1:8000/api/v1/places?city_id=kazan&category_id=food&limit=20'
curl 'http://127.0.0.1:8000/api/v1/places/map?min_lat=55.7&max_lat=55.9&min_lon=37.4&max_lon=37.8&limit=200'
```

Для поиска используется встроенная Unicode-коллация `pg_unicode_fast` PostgreSQL 18. Показ координаты сохраняет исходные `kind` и `entrance_verified`. Готовность места отражает отдельное поле `route_ready`. Все карточки текущего каталога имеют `route_ready=false`. При использовании данных OSM отображайте атрибуцию из ответа и сохраняйте сведения об источниках.

При ошибке БД API возвращает 503. Подробности записываются в серверный журнал.

## Поездки и гостевой доступ

Гостевая сессия владеет набором поездок. Создайте её через `POST /api/v1/guest-sessions` и сохраните `access_token` на клиенте. Ответ содержит `token_type=bearer` и заголовок `Cache-Control: no-store`. В БД хранится SHA-256-хеш токена. Токен содержит 32 случайных байта, выдаётся при создании сессии и действует до удаления записи сессии из БД. Утрата токена означает утрату доступа к гостевым поездкам. Передавайте его через HTTPS при развёртывании сервиса.

Во всех запросах к поездкам передавайте заголовок `Authorization: Bearer <access_token>`. Swagger поддерживает ввод токена через кнопку Authorize. Каталог доступен публично. Список поездок содержит поездки текущего гостя. Обращение к чужой поездке возвращает 404.

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/v1/guest-sessions` | Создать гостевую сессию, ответ 201 |
| `POST /api/v1/trips` | Создать поездку, ответ 201 |
| `GET /api/v1/trips` | Список своих поездок с `limit` и `offset` |
| `GET /api/v1/trips/{trip_id}` | Поездка со всеми днями и местами |
| `PATCH /api/v1/trips/{trip_id}` | Обновить название, город и даты |
| `PUT /api/v1/trips/{trip_id}/itinerary` | Атомарно заменить программу поездки |
| `DELETE /api/v1/trips/{trip_id}?expected_revision=1` | Удалить поездку с остановками, ответ 204 |

### Создание поездки

Сначала получите токен, затем создайте поездку. Значения в угловых скобках замените результатами предыдущих запросов.

```bash
curl -X POST http://127.0.0.1:8000/api/v1/guest-sessions

curl -X POST http://127.0.0.1:8000/api/v1/trips \
  -H 'Authorization: Bearer <access_token>' \
  -H 'Content-Type: application/json' \
  -d '{"title":"Выходные в Казани","city_id":"kazan","start_date":"2026-12-05","end_date":"2026-12-06"}'
```

Дата начала и окончания включены в поездку. Допускается от 1 до 366 дней. `title` содержит от 1 до 200 символов после удаления пробелов по краям. Город должен существовать в каталоге. Ответ содержит UUID поездки, `revision=1`, временные метки с часовым поясом и массив `days`. Каждый день содержит `day_number`, календарную `date` и `stops`, включая пустые дни.

### Сохранение программы

`PUT /itinerary` принимает всю программу поездки. Порядок элементов `stops` задаёт порядок посещения. Для переноса места между днями переместите соответствующий объект в другой день и отправьте обновлённую программу. Дни, пропущенные в запросе, становятся пустыми. `days=[]` очищает программу.

```json
{
  "expected_revision": 1,
  "days": [
    {
      "day_number": 1,
      "stops": [
        {
          "place_id": "<id места из каталога Казани>",
          "duration_minutes": 60,
          "notes": "Посетить утром"
        }
      ]
    }
  ]
}
```

У остановки есть UUID `id`. Сервер создаёт его, если поле пропущено. При редактировании передавайте ID из предыдущего ответа для сохранения идентичности остановки. Клиент также может создать UUID самостоятельно. UUID остановки уникален во всей БД. Одно место может посещаться несколько раз с разными UUID остановок.

`day_number` начинается с 1 и ограничен длительностью поездки. В запросе допускается до 100 остановок в день. `duration_minutes` содержит от 1 до 1440 минут, `null` означает, что длительность ещё предстоит определить. `notes` содержит до 2000 символов. Каждый `place_id` должен принадлежать городу поездки. Ответ содержит `position`, начиная с 1, и вложенную краткую карточку `place`. Атрибуция OSM возвращается в поле `attribution` поездки.

### Версии и изменения дат

Каждая успешная операция `PATCH` или `PUT` увеличивает `revision` на 1. В теле передавайте текущее значение через `expected_revision`, при удалении — через query-параметр. Если версия устарела или возник конкурентный конфликт PostgreSQL, сервер возвращает 409. Получите свежую поездку и согласуйте изменения перед следующей отправкой. После сетевого сбоя проверьте актуальную версию через GET.

`PATCH` принимает `expected_revision` и изменяемые поля `title`, `city_id`, `start_date`, `end_date`. Явный `null` в этих полях вызывает 422. При сдвиге даты начала номера дней сохраняются, календарные даты пересчитываются. При сокращении поездки остановки должны помещаться в новый диапазон дней. При смене города все остановки должны принадлежать новому городу. Конфликт с существующей программой возвращает 409. Сначала скорректируйте программу, затем отправьте изменение дат или города с новой версией.

### Ошибки

- `401` — токен отсутствует или недействителен.
- `404` — поездка отсутствует или принадлежит другому гостю.
- `409` — версия устарела, возник конкурентный конфликт, занят UUID остановки или программа конфликтует с новыми датами/городом.
- `422` — некорректный запрос, неизвестный город, место из другого города или день за пределами поездки.
- `503` — ошибка обращения к БД. Подробности доступны в журнале сервера.

### Хранение и транзакции

`guest_sessions` содержит владельца и хеш токена. `trips` содержит владельца, город, название, даты и версию. `trip_stops` содержит UUID остановки, поездку, день, позицию, место, длительность, заметку, `pinned` и `visit_mode`. Календарные дни вычисляются из дат поездки. Удаление поездки каскадно удаляет остановки. Карточки мест читаются из актуального каталога при запросе поездки.

Запись выполняется в транзакции `REPEATABLE READ`. Перед редактированием блокируется строка поездки. Фиксация транзакции происходит до отправки успешного ответа. Ошибка на любом этапе откатывает изменения. Сериализационные конфликты, взаимные блокировки и нарушения уникальности возвращают 409.

## Генерация маршрутов

Все три операции возвращают предпросмотр на срок от 1 до 14 дней и требуют гостевой токен.

| Запрос | Входные данные |
| --- | --- |
| `POST /api/v1/route-plans` | ID города и даты поездки |
| `POST /api/v1/trips/{trip_id}/itinerary/rebuild` | Версия поездки `expected_revision`. Город и даты берутся из поездки владельца |
| `POST /api/v1/route-templates/{template_id}/adapt` | Новые даты. Город берётся из импортированного шаблона по ID |

Во всех трёх запросах можно передать `preferences` или текст `wishes` до 2000 символов. Без обоих полей используются значения по умолчанию. Пример запроса со структурированными параметрами работает сразу после миграции и импорта.

```bash
curl -X POST http://127.0.0.1:8000/api/v1/route-plans \
  -H "Authorization: Bearer $TRAVEL_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{
    "city_id": "kazan",
    "start_date": "2026-12-07",
    "end_date": "2026-12-08",
    "preferences": {
      "preferred_categories": ["architecture", "walking"],
      "excluded_categories": ["food"],
      "day_start": "10:00",
      "max_stops_per_day": 3,
      "max_walking_minutes_per_day": 45
    }
  }'
```

Категории берутся из `GET /api/v1/categories`. `preferred_places` и `excluded_places` принимают ID и фрагменты названий. По умолчанию день длится с 09:00 до 19:00 по времени города и включает до 4 посещений и 90 минут переходов. Предпочтения влияют на приоритет, исключения применяются при подборе. У адаптированного маршрута приоритет имеют подходящие остановки шаблона. При несовместимости с исходным днём генератор пробует другие даты поездки и сообщает о пропущенных местах. Исходные `status` и `route_ready` возвращаются в поле `template`.

Для разбора текста установите и запустите Ollama, затем выполните `ollama pull qwen3.5:4b`. Для запуска из CLI используйте `ollama serve` в отдельном терминале. Настройки `OLLAMA_URL`, `OLLAMA_MODEL` и `OLLAMA_TIMEOUT_SECONDS` задаются в `.env`. Модель извлекает предпочтения по JSON Schema. Город и даты задаёт пользователь в структурированном запросе или берёт из поездки либо шаблона. Неподдержанные пожелания попадают в `preferences.unhandled_requests`. Тайм-аут и недоступность модели дают 503, некорректный результат модели даёт 502. В обоих случаях можно повторить запрос с `preferences`. [Установка Ollama на Windows](https://docs.ollama.com/windows) · [Структурированные ответы Ollama](https://docs.ollama.com/capabilities/structured-outputs)

Для расчёта по дорожной сети задайте `OSRM_URL` в `.env`. Подготовьте граф для поддерживаемых городов с профилем `foot.lua` и включите матрицу расстояний и длительности. OSRM получает до 80 координат каталога за запрос. При отсутствии настройки или сбое OSRM ответ содержит `routing_source=estimate`. Оценка использует расстояние по прямой с коэффициентом 1,25 и скорость 4,5 км/ч. Если OSRM сообщил об отсутствии пути, переход исключается. [Документация OSRM Table API](https://project-osrm.org/docs/v26.6.1/http.html#table-service)

В ответе есть локальные времена посещений, расстояния, минуты переходов и ожидание между посещениями. Генератор проверяет недельное расписание, известные ежегодные и периодические закрытия, сезонность, последний вход и время освобождения зала. `hours_status` показывает, можно ли опереться на указанное расписание. `unknown` и `calendar_unresolved` требуют ручной сверки. `needs_booking` отмечает посещения с бронированием или входом по сеансу. В `warnings` указаны пустые дни, пропуски шаблона и пожелания, которые не удалось применить. Результат остаётся черновиком с учётом полноты каталога.

Для сохранения предпросмотра выберите из каждого дня `day_number` и `stops`. Для каждой остановки передайте `id`, `place_id`, `duration_minutes`, `notes`, `pinned` и `visit_mode`. Отправьте эти дни и актуальный `expected_revision` в `PUT /api/v1/trips/{trip_id}/itinerary`. Для нового маршрута сначала создайте поездку. Для перестроения используйте версию из предпросмотра. При 409 перечитайте поездку и повторите операцию.

`pinned: true` закрепляет остановку. Перестроение сохраняет её день, относительный порядок среди закреплённых остановок, UUID, место, длительность и заметку. Часы посещения рассчитываются заново. При конфликте закрепления с расписанием или лимитами API возвращает 409. Закреплённая остановка сохраняется даже при исключении её из предпочтений, и ответ сообщает об этом в `warnings.pinned_excluded_places`. Чтобы снять закрепление, передайте `pinned: false` при обновлении программы. Для существующего UUID пропуск поля сохраняет закрепление. Пропуск `visit_mode` сохраняет ранее заданный режим для того же места, а `null` сбрасывает его на режим из каталога.

## Проверки

```bash
uv run ruff check backend
uv run pytest -q -m "not integration"
```

Интеграционные тесты помечены `integration`. Они создают временную схему PostgreSQL и применяют миграции. Для проверок API дополнительно запускается HTTP-сервер на свободном локальном порту. После тестов схема удаляется, сервер останавливается. Для подключения нужны права создания и удаления схемы.

Укажите URL тестового PostgreSQL в переменной `TRAVEL_TEST_DATABASE_URL`. Значение ниже подходит для стандартного порта из `.env.example`. Для вашей локальной настройки замените порт.

```bash
TRAVEL_TEST_DATABASE_URL='postgresql+psycopg://travel:travel@localhost:5432/travel' uv run pytest -q
```

```powershell
$env:TRAVEL_TEST_DATABASE_URL = 'postgresql+psycopg://travel:travel@localhost:5432/travel'
uv run pytest -q
```

Быстрые тесты проверяют расписания и лимиты, разбор пожеланий и обработку ошибок провайдеров через HTTP-заглушки. Полный набор также проверяет применение миграций, гостевой доступ, изменение поездок, откат и конкуренцию записей, каталог, адаптацию шаблона и сохранение перестроенного маршрута. При запуске без `TRAVEL_TEST_DATABASE_URL` интеграционные проверки пропускаются.

В `metrics` возвращаются времена запроса `total_ms`, разбора текста `model_ms` и расчёта переходов `routing_ms`, а также количество посещений, непустых дней, закреплений, неопределённых расписаний и проверок бронирования. Метрики также доступны в журнале генератора.

Локальный замер 22 ноября 2026 года на PostgreSQL 18.6 включал 32 последовательных запроса после прогрева, по два на каждый из 16 городов. Параметры замера — 7–8 декабря, до 3 посещений и 90 минут ходьбы в день, приоритет `architecture` и `walking`. При структурированном вводе и оценочных переходах p50 составил 11,35 мс, p95 — 14,68 мс по `total_ms`. Заполнены 64 из 64 дней, оба приоритета совпали в 14 из 32 запросов. Все 186 запланированных посещений потребовали сверки расписания. Живой запрос OSRM между двумя точками Казани вернул 694 м и 10 минут. Разбор пожеланий проверен через HTTP-заглушки. Качество и скорость самой Qwen3.5 4B остаётся измерить с запущенным Ollama.
